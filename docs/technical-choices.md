# Technical choices

The technical choices of the [roadmap](../roadmap.md), with their reasons: one section per topic, its choice then its reason. List the headings first (`grep -n '^#' docs/technical-choices.md`), then read only the sections the work needs.

## Graphical interface

**Choice.** [egui](https://github.com/emilk/egui) with `eframe`

**Reason.** Pure Rust, one executable per system without an embedded browser. The interface is redrawn every frame with the available size, so the layout can change with the window width in a few lines. Supports resizing, always on top, restoring the window size and position, and animating a value over time (`ctx.animate_bool`), for the hover effects. Tauri was rejected: HTML and JavaScript, and an embedded browser that is often fragile on Linux. The OpenGL renderer (`glow`) is used rather than `wgpu`: lighter, and enough for a flat 2D interface. In debug builds, the dependencies are optimized (`[profile.dev.package."*"]`), so that the images decode and the window stays smooth during development.

## Visual style

**Choice.** The tokens of the [Visual style](../specs.md#visual-style) in one Rust module, applied to the egui `Style` and `Visuals`

**Reason.** The mock-up and the application share the same values; changing a color or a size happens in one place.

## Fonts

**Choice.** Manrope and JetBrains Mono, embedded in the executable from `assets/fonts/`

**Reason.** Both under the SIL Open Font License; the interface looks the same on every system, without depending on the installed fonts.

## Icons

**Choice.** White SVG files tinted at runtime (`assets/icons/`, from [Lucide](https://lucide.dev), ISC license), the emblem from `assets/logo/`, rendered with `egui_extras` (SVG and PNG loaders); the simplest marks (chevron) are drawn with egui lines

**Reason.** SVG icons stay sharp at any display scale, and tinting one white file gives each state its color.

## Linux display

**Choice.** X11 (XWayland under Wayland), chosen with `winit` when the event loop is built

**Reason.** The game runs through Proton as an X11 client, so an X11 application can read what it copies without having the focus; a native Wayland application can't always read the clipboard in the background. To be verified on Bazzite KDE in step 2. winit would pick Wayland otherwise (a dependency of eframe enables it), and the OpenGL renderer is only built for X11.

## Clipboard

**Choice.** [`arboard`](https://github.com/1Password/arboard), polled every 250 ms on its own thread, which sends the copied items to the interface through a channel and wakes it up

**Reason.** Same API on Windows, macOS and X11, for reading the items and writing the whispers. Polling is simple and enough to react before the player looks at the window. On its own thread, a slow reading (under X11, the owner of the clipboard has to answer) never freezes the window, and the window only redraws when an item arrives. Only a hash of the last text is kept, not the texts copied outside the game. Two copies of the same item in a row leave the same text: change counters of each system (Windows, macOS) could tell them apart later, if needed. The copies and the pastes in the fields of egui reach the system only with the `clipboard` feature of eframe: it is off with `default-features = false`, and then the text stays inside the application, with no error. A check of the CI (`.github/scripts/system-clipboard.sh`) keeps it on for every target of the release. A paste in a field (Ctrl+V, the middle button on Linux) reads on the thread of the window, through egui-winit: under X11, an owner of the clipboard that doesn't answer can freeze the window for up to about 28 seconds.

## Price-check hotkey (Linux, Windows)

**Choice.** [`global-hotkey`](https://github.com/tauri-apps/global-hotkey) to hear Ctrl+D (XGrabKey on the root window of X11, RegisterHotKey on Windows), the copy sent with the XTest extension of [`x11rb`](https://github.com/psychon/x11rb) at the release of D (step 14a1), with SendInput through [`enigo`](https://github.com/enigo-rs/enigo) at its press on Windows (step 14a2)

**Reason.** Under X11 (XWayland under Wayland), an application hears and sends keys while an X11 window, the game run by Proton, has the focus, as Exiled Exchange 2 does on Linux (uiohook). `global-hotkey` also covers Windows (RegisterHotKey), step 14a2, and macOS (Carbon), left out while Path of Exile 2 has no macOS client. The copy is sent once D is released: while the key is held, the passive grab gives every key to the application, so that a copy sent then wouldn't reach the game. The XTest keys are written with x11rb rather than `enigo`: it reads whether Ctrl is still held (QueryPointer), so as never to release a Ctrl the player holds (the next D would then reach the game alone), and never remaps a free keycode, which `enigo` does for a key missing from the layout. Checked on Bazzite KDE on 2026-11-01 with `xdotool` (an X11 window focused: heard and sent; a Wayland window focused: not heard); checked in the game by the owner the same day (every test passed, the class of the game `steam_app_2694490`). A key grabbed can't be given back to the window that has the focus: since step 14c1, it is grabbed only while the game is the active window (`_NET_ACTIVE_WINDOW`, followed on a thread of its own through the `PropertyNotify` events of the root window, and of the active window for its class and title, which a window may set after it shows), released when another window becomes active (`register` and `unregister` of `global-hotkey`, which grab and ungrab on its own connection), so that Ctrl+D stays to the other windows; the game told by its class `steam_app_2694490` (Proton) or its exact title `Path of Exile 2` (the standalone client run by Wine, whose class is unknown; the title Exiled Exchange 2 looks for, never a part of it, which a page of a browser would match). No active window told (`Active::Unknown`: a Wayland window, or maybe the window over the game holding the keyboard on a desktop other than KWin, as `src/overlay/keyboard.rs` allows) leaves the key as it is, so that Ctrl+D still gives the keyboard back to the game; a key grabbed under X11 never reaches a Wayland window anyway. A desktop without `_NET_ACTIVE_WINDOW` in `_NET_SUPPORTED`, or the X server lost, falls back to the key grabbed for every window, written to the log. The root window written as the active window is never followed, its events of the active window being turned off otherwise. `WM_NAME` read of any type (Wine may write it in UTF-8). The class of each other active window written to the log once, never its title, so that the class of the standalone client can be found. The rules of the grab are written without the system (`src/hotkey/grab.rs`), tested, like the choice of the events followed (`matters` in `src/hotkey/x11/active_window.rs`); a failed grab (the key taken) is tried again at each activation of the game, written to the log once until it changes. On Windows, RegisterHotKey takes D alone and grabs no other key: the copy is sent at the press of D, C alone while the player holds Ctrl, as Exiled Exchange 2 does there (`pressKeysToCopyItemText` with `keepModKeys` in `main/src/shortcuts/Shortcuts.ts`); since step 14b3a, the clipboard is prepared first (the marker, as on Linux), which may outlast a short press of Ctrl, so that Ctrl is read just before the keys (`GetAsyncKeyState` of `winsafe`) and pressed around C when the player released it. `enigo` rather than the `windows` crate, whose calls are `unsafe`, forbidden in the application; it sends the virtual key of C, which Windows maps to the layout of the window that has the focus. Windows drops without a word the keys sent to a window of higher integrity (the game run as administrator): the log then says the copy was requested, not received. Since step 14c2, the key is registered only while the game is the foreground window (`register` and `unregister` of `global-hotkey`, on the thread of the window, since `RegisterHotKey` takes a window of the thread that calls it, here the hidden window of `global-hotkey`), the same rules as on Linux (`Grab` of `src/hotkey/grab.rs`); the game told by its exact title `Path of Exile 2`, as Exiled Exchange 2 does (`attachByTitle`), the client of Steam and the standalone one alike. Windows tells the changes of the foreground window only to a hook (`SetWinEventHook`), whose callback can't be written without `unsafe`, and a message loop of a thread of its own would need `DispatchMessage`, `unsafe` in `winsafe` too: a thread reads `GetForegroundWindow` every 50 ms (a few microseconds each) and sends each change to the thread of the window, woken by a repaint, which registers or unregisters the key in `App::logic` (eframe still runs it while the main window is minimized, ten times a second at most); the key is registered within 50 ms of the game coming to the front (150 ms while the main window is minimized). A window of this process in front (`GetWindowThreadProcessId`; its title never read, a message to the thread of the window) is the main window while egui tells that it has the keyboard (`ViewportInfo::focused` of the root viewport, read in `App::logic`), which releases the key, as another window; otherwise the window over the game, which keeps it as it is (`Foreground::active`), so that Ctrl+D still copies while one of its fields is edited. Told apart by egui rather than by whether the window over the game shows: the poll may miss the switcher of Alt+Tab between them (code review of 14c2). No foreground window, as Windows tells for a moment while it changes, leaves the key as it is. A window titled `Path of Exile 2` of the class of the File Explorer (`CabinetWClass`, the folder of the game) isn't the game, so that Ctrl+D never copies its files. The key follows each change of the active window once (`ForegroundFollow` of `src/hotkey/grab.rs`, tested on Linux), so that a key taken by another application is tried again at the next change, not at each frame. A thread that can't start, or stops, falls back to the key registered for every window, as before. The class of each foreground window written to the log once (`GetClassName`), of the game too, so that the window taken for it can be checked; never its title. Not checked in the game on Windows: the owner has none. The CI of the pull requests runs Clippy on Windows, and for macOS from Linux (`scripts/clippy-macos.sh`), so that the code of these systems is checked before a release; the real build for macOS is the Release workflow, not required on a pull request. Since step 14c3b1, the keys come from the settings (`Shortcut` in `src/hotkey/shortcut.rs`, its own type rather than the `HotKey` of `global-hotkey`, whose parsing takes any key, so that the rules of the keys allowed are the application's and the key caps have their names). A Shift held when the copy leaves (left and right) is released first and pressed again last (`Held` and `copy_keys` in `src/hotkey/sent_keys.rs`, tested), since Ctrl+Shift+C isn't the copy: Exiled Exchange 2 releases the keys of its hotkey before the copy too, but never presses them again (`pressKeysToCopyItemText` and the `keyToggle` of `register` in `main/src/shortcuts/Shortcuts.ts`, read on 2026-11-03), which would make the next D of a player who holds the modifier reach the game alone. An Alt held stays held (code review of 14c3b1): Ctrl+Alt+C is the advanced copy, the same text as Ctrl+C in the game, and Exiled Exchange 2 sends it on purpose (`showModsKey`); under X11 the copy leaves at the release of D, when the player often releases Alt too, and an Alt pressed again in the 60 to 85 ms the keys take could stay held for the X server. Ctrl+Alt+C is then refused as a hotkey, which the copy would press. The Shift keeps that race, rarer (Ctrl+Shift+D released at once): an unexpected Shift pressed again is held until the player presses it again. Under X11, the keys held are read with `QueryKeymap` and their keysyms from the first column of the keyboard mapping (Meta too, which some layouts give to Alt); a modifier of the hotkey no longer held is released once more (`missed_modifiers`), since the active grab of the key took its release from the game; the X server may drop the release of a key it already holds released, which the test of an Alt released before D (the guide of 14c3b1) checks. After a failure, only the releases are sent, so that a modifier is never pressed again by a copy that failed: at worst the player presses it again.

## Writing the clipboard

**Choice.** `clipboard::write_text`, through `arboard`, rather than `egui::Context::copy_text` (forbidden in `clippy.toml`)

**Reason.** `copy_text` runs after the frame, inside egui-winit, and only logs a failure: "Copied" would show even when nothing was written. `arboard` gives its result at once and barely blocks the window: it takes the selection under X11, and tries for about 25 ms on Windows when another application holds the clipboard. Under X11, `ClipboardWatch` keeps a handle open, so that closing the one of a copy doesn't end the ownership of the text. A success means that the system took the text (under X11, that the request was sent), not that another application can paste it: the failure shows on Windows above all.

## Hotkey turned on or off, its key taken (step 14c3a)

**Choice.** The rules of the grab kept in `Grab` (`src/hotkey/grab.rs`), the system calls given as closures; turned on or off by `Grab::turn`, which remembers the last active window to grab the key at once in the game; on Linux, the `Grab` shared through an `Arc<Mutex>` between the thread that follows the active window and the thread of the window, held across `register` and `unregister`, whether the key is taken published in an `AtomicBool` that each frame reads without the lock; whether the hotkey is on, an `AtomicBool` read by the handler of the hotkey events; what the window shows told by one `HotkeyState` (listening, off, taken, unavailable)

**Reason.** The rules stay tested without a system, as in step 14c1. One lock keeps whether the hotkey is on, its key held and its failure in step, whichever thread changes them first; the follow thread holds it while `global-hotkey` answers (up to 50 ms), which a frame must never wait for. The handler ignores a press while the hotkey is off, even when releasing its key failed, without taking any lock. Exiled Exchange 2 grabs Ctrl+D each time the game becomes the active window too (`main/src/shortcuts/Shortcuts.ts`, checked on 2026-11-03): with both running, the first to grab it keeps it, so that the key may be taken at one activation of the game and free at the next.

## Window over the game (Linux, step 14b1)

**Choice.** A second egui viewport, an X11 window *override-redirect* (`with_override_redirect`, `with_window_type(Tooltip)`, `with_active(false)` of `egui::ViewportBuilder`), placed from the pointer and the active window read through `x11rb` (`QueryPointer`, `_NET_ACTIVE_WINDOW`, `GetGeometry`); the click in the game that closes it seen by polling the buttons of `QueryPointer` while it is open

**Reason.** The way of Exiled Exchange 2 on Linux (electron-overlay-window sets override-redirect before mapping): the window manager doesn't manage the window, so KWin keeps it above the fullscreen game and never gives it the focus. Checked in the owner's game on 2026-11-01 with a throwaway probe (Bazzite KDE, windowed fullscreen, the game an X11 window of 2560 × 1440 with `_NET_WM_STATE_FULLSCREEN`, scale 1): the window shows over the game, the game keeps the keyboard, and a click on the window stays in it without reaching the game nor taking its focus. In exclusive fullscreen, the game copies nothing at Ctrl+D and D reaches it: not supported, as in Exiled Exchange 2. eframe 0.37 can't create a window while the main one is minimized (it then paints from outside of its event loop, and egui panics when the window of an immediate viewport isn't drawn): the window is created hidden with the first frame and only shown or hidden afterwards, and `ViewportCommand::RequestPaintWhileHidden` runs the interface while the main window is hidden. No new dependency. Windows in step 14b3: a window always on top shown without activation (`with_active(false)`), but winit can't make it never activated (`WS_EX_NOACTIVATE`) and `unsafe` is forbidden, so a click in it may take the focus of the game, to give back.

## Keyboard of the window over the game (Linux, step 14b2)

**Choice.** `SetInputFocus` of `x11rb` on the window over the game while one of its fields is edited (`Context::text_edit_focused` of egui in its viewport), back to the active window of the desktop afterwards; the window found under the pointer at the click (`QueryPointer`, override-redirect, its `_NET_WM_PID` this process); the hotkey gives the keyboard back to the game before the copy when a window of this process has it

**Reason.** The window manager never gives the keyboard to a window it doesn't manage: the application sets the input focus itself, as Exiled Exchange 2 does (`xcb_set_input_focus`). Checked in the owner's game on 2026-11-01 with a throwaway probe: KWin leaves the keyboard to the window (still there 3 s later), keeps the game as its active window (`_NET_ACTIVE_WINDOW`), and the game takes the keyboard back without a hitch; when the window hides, the X server gives the keyboard to the root window (revert to parent), from where it goes back to the game. eframe gives no X11 id of a viewport: read under the pointer, where the click on the field just was. Given back only from the window, the root or no window, and while the game is still the active window, so that a keyboard the desktop gave meanwhile to another window (a click in the main window, Alt+Tab) stays there; a desktop that tells no active window meanwhile (KWin keeps the game; GNOME and the others unchecked, to try before the first release) gets it back from the window only. The hotkey gives the keyboard back to the game before its copy from a window of this process that the desktop didn't activate, or from no window (the window over the game just hid), never from the window under the pointer (`PointerRoot`, a mode of the window manager). egui keeps a field focused when its window loses the keyboard: the field is left then (`WindowFocused(false)`); a shortcut of the desktop grabbed while a field is edited (the volume, Print Screen) also takes the keyboard for a moment under X11, so that it leaves the field too, which the player clicks again. The X11 reads shared by the hotkey and the window over the game (the atoms, the active window, the windows of this process, the keyboard in no window) are in `src/x11.rs`. No new dependency.

## Window over the game on a single screen (Linux, fix after step 17a)

**Choice.** At each opening, and four times a second for 3 s after, an `InputOnly` override-redirect window of another client covering the X screen above the game (or its frame) tells, without touching the pointer, that Wine may hold it; `GrabPointer` on the root window (let go at once) then confirms it. If so, a helper window of `x11rb` (1 × 1 under the window over the game, managed by the desktop, `_MOTIF_WM_HINTS` without functions nor decorations so that Alt+F4 can't close it, `WM_DELETE_WINDOW`, `_NET_WM_WINDOW_OPACITY` 0, `_NET_WM_STATE_SKIP_TASKBAR`/`_SKIP_PAGER`, `WM_TRANSIENT_FOR` the game, `_EXILE_MARKET_GAME` the game) is activated with a `_NET_ACTIVE_WINDOW` client message (source 2), then the window over the game takes the keyboard (`SetInputFocus`), and drops every key but Esc from its frames unless a field is edited; the game is activated again at its closing with Esc when the helper still is. The hotkey takes the helper for the game, activates the game again before its copy, and counts its press as on its way before (an atomic counter, read after the active window), so that the window neither takes the game made active for Alt+Tab nor becomes active during the copy (`src/overlay/activation.rs`, `src/overlay/activation/x_screen.rs`, `src/hotkey/x11/active_window.rs`, `src/hotkey/x11/copy.rs`, `src/hotkey.rs`).

**Reason.** Wine holds the pointer of a fullscreen game alone on its screen and lets it go only when another window becomes the active window of the desktop; `SetInputFocus` alone doesn't (probes in the owner's game on 2026-11-07). eframe can't make the window over the game a managed window without creating it again, which panics while the main window is minimized: a window of its own is activated instead. `WM_TRANSIENT_FOR` keeps the game above the taskbar in `KWin`, which leaves a fullscreen window in its top layer while the active window is one of its own. Only while the grab is held, so that two screens or a game in a window keep the keys of the game.

## Window over the game (Windows, step 14b3a)

**Choice.** The same egui viewport, always on top (`WindowLevel::AlwaysOnTop`, `WS_EX_TOPMOST`), shown without activation (`with_active(false)`: winit shows it with `SW_SHOWNOACTIVATE` each time), out of the taskbar; the pointer, the buttons of the mouse, Ctrl and the game window read through [`winsafe`](https://github.com/rodrigocfd/winsafe) (`GetCursorPos`, `GetAsyncKeyState`, `GetForegroundWindow`, `GetClientRect` and `ClientToScreen`); the focus given back to the game after a click in the window (`SetForegroundWindow`)

**Reason.** `winsafe` wraps the Win32 calls in a safe API (MIT), while those of the `windows` and `windows-sys` crates are `unsafe`, forbidden in the application; its `SetWindowLongPtr` stays `unsafe`, so that the window can't be made never activated (`WS_EX_NOACTIVATE`): a click in it activates it, and the application gives the focus back to the foreground window seen while the window showed without it, the game (never a window of this process), as Exiled Exchange 2 does (`focusTarget` of electron-overlay-window), once the buttons are released, so that the window still gets the release of its click, and after its content, so that a click that opens a link (Check on trade) leaves the foreground to the browser instead; Windows allows it while this process has the foreground, as just after that click. The window is placed with the scale of its own screen, which egui-winit converts its points back with (each screen has its own scale on Windows), the one of the main window until it exists; read at the previous frame, so that at its first opening on a screen of another scale, the window may be placed wrong for a frame (second code review of 14b3a): the scale of the game read at the hotkey (`GetDpiForWindow`) would size it right, but egui-winit converts the position with the scale of the screen the window is on, which only the tester can tell (whether a hidden window moved to another screen takes its scale at once), so that it waits for the tester's report. The class of the foreground window is written to the log at each copy, never its title (a page of a browser, which may say what the player reads). The marker kept out of the clipboard managers that honour it too (`exclude_from_monitoring` of arboard, the format `ExcludeClipboardContentFromMonitorProcessing`). The clicks in the game polled like under X11 (the click watch shared by both systems), every 20 ms, without a hook of the mouse; a pointer that can't be read for a moment (the secure desktop, the session locked) reads as no button held, so that the window isn't turned off for good. The game window measured inside its frame (its client area), in physical pixels, winit making the process aware of the scale of each screen. Since step 14b3b, a click in a min or max field keeps the focus until no field is edited (Enter, Esc, a click elsewhere in the window), then the window gives it back the same way; the game is remembered in a static shared with the hotkey (rather than an `Arc` given to both, so that the hotkey starts with the same signature on every system; the handle, which can't be copied without `unsafe`, `raw_copy` of `winsafe`, stays in one place), so that Ctrl+D while a field is edited brings the game back to the front (`SetForegroundWindow`, allowed while the window over the game has the foreground) before the keys of its copy, with Ctrl pressed once more (never released) when the player holds it, since the game, activated after the press of Ctrl, may not count it as held (Ctrl read just before the keys, so that one released meanwhile isn't left held); when Windows refuses to bring the game to the front, the hotkey copies nothing, so that the marker never replaces the item of the player for a copy that can't succeed. These rules are written without the system too, tested on Linux (`give_keyboard_back` in `src/overlay/game_focus.rs`, `copy_keys_after_focus` in `src/hotkey/sent_keys.rs`). The rules of the focus given back are written without the system (`src/overlay/game_focus.rs`), tested on Linux. Not checked in the game on Windows: a tester of the owner tries the build of the pull request (the archive of the release workflow). Unknown until then: whether `GetAsyncKeyState` reads the buttons while a game run as administrator has the focus, whether the window shows in Alt+Tab or comes back to the taskbar (winit leaves it out of the taskbar once, at its creation), and whether a game that sets itself always on top covers it.

## Price database

**Choice.** [poe2scout](https://poe2scout.com) public API (`https://api.poe2scout.com`, [Swagger](https://api.poe2scout.com/swagger))

**Reason.** Covers the currency exchange items and the uniques of Path of Exile 2, gives the number of offers, the 7-day history, the leagues and the Exalted / Divine / Chaos rates. poe.ninja was rejected: its documentation asks desktop applications to go through their own backend rather than call its API from the players' machines. The prices are downloaded per category and cached, behind a trait, so that the source can change.

## Price cache

**Choice.** One JSON file per league in the cache directory (`serde_json`), with a version number, written to a new file then renamed

**Reason.** The prices show at once at startup, and while the price database can't be reached; prices younger than an hour are not downloaded again at a new launch. A file of another version (the shape of the prices changed) is downloaded again rather than migrated.

## Price estimation

**Choice.** Two functions, no trait: `price::fixed::price_of` gives the price of a fixed-name item from the price database as an `enum` (`FixedPrice`: a currency, a unique, several possible uniques), or says why there is none (`NoFixedPrice`); `NotFixedName` sends the item to `Estimate::of` (`price::estimate`), which estimates it from similar offers of the trade site

**Reason.** The two ways take and give different things: a `Result` whose error says why is enough, and each kind of item gets its price its own way without changing the parser or the interface (a trait per way of pricing was the first idea, never needed; core review of 2026-11-10).

## Item parser

**Choice.** A hand-written parser, section by section, with the words of each language in one table per language (`src/item/labels.rs`, from the client strings of Exiled Exchange 2, checked on copied items); no regular expressions

**Reason.** The structure of a copied item is the same in every language: only the words change, and adding a language is adding a table. Without dependency, and the Clippy lints that forbid what can panic (indexing, `unwrap`) apply to the whole parser, which reads every copied item.

## Copy format

**Choice.** The advanced copy (the `{ … }` header of each modifier), and the copy of the trade of the game, without headers (step 13k2e): its lines read alone, as explicit modifiers without affix, tier nor range, those whose marker tells it as fractured, desecrated or Vaal (` (mutated)`); the affix and the tier of each found from its value in the modifier tables of the base (step 13k2e3)

**Reason.** The headers give the tier and the ranges of each modifier, which the roll bars, the range fields and the modifier tables need. The game writes them with Ctrl+C too (checked on 2026-10-28), but not for an item copied from the trade of the game (another player's listing, checked on 2026-10-28), which the parser refused until step 13k2e2: Exiled Exchange 2 reads it, each line alone (commit cca3066). The ranges of a unique come from the copy, or from poe2scout for a unique copied from the trade of the game, which has none (step 13k2e5): poe2scout writes the modifiers of each unique with their ranges in the answer already downloaded with the prices, kept in the price cache, and each copied line is matched with one of them by its stat, so that a French copy gets them too (the database writes in English only); Exiled Exchange 2 shows these lines as fixed and searches the unique by its name.

## Offers

**Choice.** Official trade site API: `POST /api/trade2/search/poe2/<league>` then `GET /api/trade2/fetch/<ids>?query=<search id>&realm=poe2` for items (10 ids per fetch, from the ids of the search, the cheapest first), `POST /api/trade2/exchange/poe2/<league>` for the currency exchange (its offers in the answer, without fetch), on the trade site of the language of the item; the same queries as the links opened in the browser (`src/trade/query.rs`). Read on their own thread, which searches only when the player asks (checked on 2026-10-26); the ids left to fetch of a search go with its answer and stay with its offers (`Rest` in `src/trade/search.rs`), not in the thread, so that the list of one of the last items copied, shown again, fetches the rest of its own search, with its own search id

**Reason.** The only source of individual offers: poe2scout only gives aggregates. The fetch returns the whole listed item (modifiers with their stat ids, item level, seller status, whisper message), used by the tooltip without another request. Accepted with guardrails despite the Terms of Use risk: see [Trade site usage](trade-site-usage.md).

## Trade site limits

**Choice.** The limits read from the `X-Rate-Limit-*` headers of every answer, before its body, one policy per kind of request (search, fetch, exchange); two times kept for each request, when it left and when its answer or failure came; the hits the trade site counts beyond ours (a browser on the same address) added as if made at the answer; a request the limits don't allow is never sent, and a refusal (429 or 403) waits for its `Retry-After` delay, a minute without one, for every request to the trade site: the searches, the next offers and the download of the item names share that wait (`Refusal`, security audit of 2026-11-10). When in doubt, the safe side: limits that can't be read keep the known ones, a request leaves the windows with the time of its answer, and only the requests the trade site counted for sure (a success with its limits, sent within the window) are taken from its counts; a margin of one second on every window and wait

**Reason.** The limits change without notice and the address may be shared: only the headers know them. Each count takes the time and the case on the safe side, so that the application never thinks a window has room the trade site doesn't give; four code reviews checked it (2026-10-26).

## Stat filters

**Choice.** The stats of the copied item become filters of the search, as in Exiled Exchange 2: the trade id of each modifier line from the stats of Exiled Exchange 2 (strings of each language, `reduced` variants, trade ids by group), embedded, and the templates of `/api/trade2/data/stats` as a second lookup; equipment filters from `/api/trade2/data/filters` (checked on 2026-10-27: the item level and the quality in `type_filters` as `ilvl` and `quality`, the DPS and the augmentable sockets in `equipment_filters` as `pdps`, `edps` and `rune_sockets`, the required level in `req_filters` as `lvl`, searched as a maximum); the states in `misc_filters` (checked on 2026-10-28: `corrupted`, `sanctified`, which isn't corrupted (2,706 rare rings sanctified and not corrupted), `mirrored` (33 rare rings), and for step 13k2d `twice_corrupted`, `fractured_item`, `desecrated`, `mutated` and `veiled`; checked on 2026-10-29 that the trade site applies `{ "option": "true" }` on the two states of step 13k2d: `fractured_item` finds 10 rare rings online, and `twice_corrupted`, none among the rare rings online but more than 10,000 items of any status, its first 10 all flagged `doubleCorrupted` and `corrupted` in their offers), the number of unrevealed modifiers as the pseudo stat `pseudo.pseudo_number_of_unrevealed_mods`, and the Runic Ward of a runeforged base in `equipment_filters` as `ward`, the category of the base searched in place of the base type when the player unchecks it (`type_filters.category`, the ids of Exiled Exchange 2, checked on 2026-10-28; a flask by its tags, `flask.life` or `flask.mana`); the ranges of a unique from the advanced copy. A modifier added by a Vaal orb on a unique (mutated, `{ Vaal Unique Modifier }`) is an explicit line of the trade site, flagged `mutated` in its offers: its explicit id finds it (checked on 2026-10-28 on Soul Tether; `/api/trade2/data/stats` has no mutated group). See [Game data](game-data.md)

**Reason.** Offers are only comparable with similar stats; the same filters price the uniques, the rare, magic and normal items and the jewels. The trade site templates alone miss the `reduced` variants and the local stats; Exiled Exchange 2 found every line of the copied items of the tests, in English and French (2026-10-26). An exceptional base is searched by its sockets and its quality: the trade site refuses its name ("Unknown item base type", checked on 2026-10-27).

## Modifier tiers

**Choice.** The tier and its range from the advanced copy; the range of every tier of a modifier from the modifiers, bases and stat texts of the RePoE fork (`mods.json`, `base_items.json`, `stat_descriptions.json`), reduced by a generator kept in the repository, committed and embedded, generated again after each patch of the game. See [Game data](game-data.md)

**Reason.** The roll bar of a rare modifier covers all its tiers, so that a full bar means close to the best possible; the advanced copy only gives the range of the current tier. RePoE gave back the tier and range of the copied items of the tests (2026-10-26) and of 374 modifiers of offers of the trade site (2026-10-27); poe2db has no API. Embedded, the data works offline and matches the parser of the same version.

## Game data

**Choice.** A generator in Rust, `tools/game-data/`, a member of the Cargo workspace (`cargo run -p game-data`), writing one stat or one base per line (NDJSON) to `assets/game-data/`; the files embedded with `include_str!` and read at the first item copied in their language; the stat of a line found by its string, its numbers written `#`

**Reason.** The language of the application, without another tool to install; one stat or base per line makes the changes of a patch readable in a diff; reading a language takes 3 ms in a release build, so no build script is needed. The release workflow takes the default member of the workspace, so that the generator is never published. See [Game data](game-data.md).

## Estimated price

**Choice.** Median of the 5 cheapest similar offers, suspicious offers excluded; an offer is suspicious under a quarter of the median of the first 10 offers, the answer to the search, fewer when some were withdrawn since the search or left out for their currency (`src/price/estimate.rs`)

**Reason.** A median resists the bait offers and the few overpriced ones; 5 offers are enough to be meaningful without extra requests (one fetch returns 10). The estimate can't tell its own suspicious offers (it leaves them out): the median of the whole first page holds while fewer than half of it are bait, which a median of the 5 cheapest wouldn't (3 baits of 5 would make the reference a bait), and it doesn't move when the next offers load.

## Estimate only from a search that compares the item (step 17e3f)

**Choice.** Each filter of a search tells what it rules out of the offers, `RulesOut` (items of the base of the item, items of the league only, nothing), decided in one place, `LineStats::rules_out` (`src/trade/stat_filters.rs`), where the lines of the item, what its base reaches and the minimum of the filter are known; the value travels with the filter (`StatFilter`, `PropertyFilter`), is never sent to the trade site, and the offers keep whether their search compared the item (`SearchedBy` in `src/offers_state.rs`). The same rule checks the totals and the DPS at first, gates the estimate of a rare or magic item, and chooses the line under "No market price…" (`StatChecks::of`, on the filters as they are, then all checked)

**Reason.** The price of the worst items of a base must never read as the price of the item: a filter any item of the base passes (its implicit, a small total, the DPS of the base) says nothing of it. One rule for the three uses, so that the checkbox, the estimate and the notice can't disagree; decided on the domain types (`FilterKey`, `ModifierKind`), not on the ids of the trade site, after a first version on the ids counted the number of unrevealed modifiers as a stat (`docs/lessons.md`, 2026-11-10). What the base reaches and its proofs: `docs/game-data.md`, "What a base reaches".

## Item names in French

**Choice.** Trade site data in both languages (`/api/trade2/data/items`, `/data/static` and `/data/stats` on `www.` and `fr.pathofexile.com`, six requests one second apart), read on their own thread, cached and refreshed once a day; the old names stay when the trade site can't be reached, with a new attempt every hour, every minute while no name is known (but not after a refusal of the trade site, 403 or 429: an hour later at the earliest, after its `Retry-After` delay, and never during the wait of a refused search); while no name is known and the trade site does answer, with an error or with names the application can't read, or stops answering after the first of the six requests, the next attempt waits 1, 2, 4… minutes, an hour at most (`Backoff` in `src/http.rs`). They go through the transport of the searches: no redirection followed. The templates of the stats (`/data/stats`) come with them since step 13d, as a second lookup of the stat of a line (see [Game data](game-data.md))

**Reason.** The price database only knows the English names. The items of the currency exchange have ids shared by both languages and by poe2scout (all of them on 2026-10-25): a French name gives the id, which gives the price, without translation. The uniques have no id, but each category lists them in the same order in both languages (771 pairs without a contradiction on 2026-10-25), checked again at each download: a category whose lists don't line up (another number of uniques, a variant in one language only, a base type paired two ways) is left out rather than paired wrong, and an answer without a kind of names keeps the cache. An unidentified unique can be each unique of its base known by the trade site, priced or not: the price database only has the uniques listed lately. The base types don't line up (some are missing in French) and need no translation: the base of a magic item is found among those of its language, and the searches use the trade site of its language.

## Images

**Choice.** Orb icons, the icons of the currency exchange, logo and emblem bundled from `assets/`; the 771 icons of the currency exchange embedded by `build.rs`, which writes the table of their ids from `assets/exchange/` (a table by hand would change at each run of `tools/exchange-icons`), each decoded by the PNG loader of `egui_extras` only once shown

**Reason.** See [Images](images.md).

## HTTP

**Choice.** [`ureq`](https://github.com/algesten/ureq) in a background thread, `serde` / `serde_json`

**Reason.** Blocking and simple; the requests are few (one price refresh per hour, one trade site search per click), so an async runtime is not needed. The interface thread is never blocked. HTTPS only, no redirection followed (but to the API of GitHub, which redirects a renamed repository), and an answer read up to 16 MB once decompressed: the limit of `ureq` counts the compressed bytes (security audit of 2026-11-10).

## Update notice

**Choice.** The GitHub REST API, `GET /repos/sylent-dev/rust-exile-market/releases/latest`, with `ureq`, once at launch on a thread of its own

**Reason.** No token: without one, GitHub allows 60 requests per hour per address, far above one per launch, and the players never sign in. `/releases/latest` leaves out the drafts and the pre-releases. The page of the release is built from the repository of `Cargo.toml` and the tag, rather than read from the answer, so that the link can only open the repository of the application. The versions compared as three numbers (`v0.2.0`, the tags of the release workflow), without a crate: a tag of another shape is ignored, written to the log. A 404 (no release yet) is no error.

## Bug report

**Choice.** The issue form `.github/ISSUE_TEMPLATE/bug-report.yml` opened in the browser (`OpenUrl` of egui, like the other links), its fields `report`, `item` and `log` filled through the address (`/issues/new?template=bug-report.yml&report=…`, the way GitHub documents to prefill a form); the address kept under about 6,000 encoded characters: the summary and the item first, then the last lines of the log that fit, written short (`src/bug_report.rs`); the version of Windows read from its registry through the `advapi` feature of `winsafe`, already a dependency for the window over the game

**Reason.** No GitHub token in the application: the player signs in to their own account and sends the issue, so that nothing is sent without them and no secret can be taken from the executable. The form gives each report the same fields and the `bug` label (set by the template, since a visitor can't set a label through the address). GitHub answers an error from about 6,900 characters (measured on 2026-11-04), hence the last lines of the log that fit and "Copy the log" for the whole of it. GitHub rather than Discord (owner's choice on 2026-11-04): Discord has no address that writes a message, a webhook would put a secret in the application, and a channel doesn't follow a bug to its fix (`fixes #12`).

## Interface translations

**Choice.** [Fluent](https://projectfluent.org) with `fluent-bundle`, files `locales/en.ftl` and `locales/fr.ftl` embedded in the executable

**Reason.** Handles the plural rules ("1 stat", "6 stats"; "0 offre", "0 offers"), and switching the language at runtime, needed by the language setting. The language of the system is read with [`sys-locale`](https://github.com/1Password/sys-locale), small and without other dependency. The interface doesn't follow the language of the copied items: it would change without the player asking (decided on 2026-10-24).

## Local files

**Choice.** [`directories`](https://github.com/dirs-dev/directories-rs) for the configuration, cache and log directories; the settings in TOML with `serde` and [`toml`](https://github.com/toml-rs/toml), written to a new file then renamed; the size and position of the window kept by eframe (`persistence` feature, `window.ron` next to the settings, without the state of the widgets)

**Reason.** Standard locations on each system. A crash while saving never leaves half a settings file. eframe brings the window back onto a connected screen when its screen is gone, which the application can't do itself: the screens are unknown before the window opens (decided on 2026-10-24).

## Log

**Choice.** The [`log`](https://github.com/rust-lang/log) facade and [`simplelog`](https://github.com/Drakulix/simplelog.rs): a file per session (the previous one kept), the error output in debug builds, the panics logged

**Reason.** The standard facade, also used by egui and eframe; `simplelog` writes a file without extra setup. Enough to follow the application and debug it on a player's machine, where there is no console.

## Price history chart

**Choice.** [`egui_plot`](https://github.com/emilk/egui_plot)

**Reason.** Made for egui, no other dependency (wide layout, step 24).

## Executable and application icon (step 17a)

**Choice.** The executable named `exile-market` by a `[[bin]]` of `Cargo.toml`, read back by the code (`env!("CARGO_BIN_NAME")`) as the application id of the window and the folder of the user's directories; the icon `assets/logo/icon.svg` rendered at each size by `scripts/app-icon.py` (`rsvg-convert` and Pillow) into `icon.png`, given to the window (`ViewportBuilder::with_icon`), and `icon.ico`, linked into the Windows executable by `build.rs` with [`winresource`](https://github.com/BenjaminRi/winresource) (`rc.exe` of the Windows SDK, with its name "Exile Market" for the File Explorer and the Task Manager)

**Reason.** One name in one place; each size rendered on its own keeps its thin lines sharp, where a large icon scaled down would blur them; the resource is compiled only when built on Windows, so that the Clippy for Windows run from Linux needs no resource compiler.

## Window that can't open (step 17a)

**Choice.** The error of `eframe::run_native` sorted into a cause (`src/window_error.rs`), its message shown by a dialog of the system: `MessageBox` of `winsafe` on Windows, `kdialog` or `zenity` run as commands on Linux, `osascript` on macOS

**Reason.** The application can't draw without its window; these dialogs need no new dependency, and those of Linux open under Wayland too, where a missing XWayland is the likeliest cause.

## Releases

**Choice.** GitHub Actions workflow triggered by version tags, portable archives (no installer)

**Reason.** Builds every system on its own runner and publishes the archives with `gh release`, without extra tooling. A portable executable is enough for version 1. The tag must be on `main`, each action is pinned to a commit and the version of Rust is pinned in `rust-toolchain.toml`, raised by Dependabot; the advisories on the dependencies are checked every day and before a release (`cargo deny`; security audit of 2026-11-10). The Linux executable targets glibc rather than musl: a statically linked musl executable can't load the system's graphics libraries (OpenGL, X11).

## License and notices

**Choice.** `GPL-3.0-or-later`; `cargo-deny` checks the licenses of the dependencies, `cargo-about` writes `THIRD-PARTY-LICENSES` at each release (step 17d2)

**Reason.** The GPL makes a fork that improves the application publish its code. `cargo-deny` only says a license is allowed; the MIT, Apache and OFL licenses ask for their notices with each copy: `cargo-about` gathers those of the libraries, and the Package step of the Release workflow copies those of the assets. The fonts, the icons of the game and its data stay under their own terms, an additional permission (section 7 of the GPL, `assets/NOTICE.md`) allowing their combination in one executable.
