# Technical choices

The technical choices of the [roadmap](../roadmap.md), with their reasons.

| Topic | Choice | Reason |
|---|---|---|
| Graphical interface | [egui](https://github.com/emilk/egui) with `eframe` | Pure Rust, one executable per system without an embedded browser. The interface is redrawn every frame with the available size, so the layout can change with the window width in a few lines. Supports resizing, always on top, restoring the window size and position, and animating a value over time (`ctx.animate_bool`), for the hover effects. Tauri was rejected: HTML and JavaScript, and an embedded browser that is often fragile on Linux. The OpenGL renderer (`glow`) is used rather than `wgpu`: lighter, and enough for a flat 2D interface. In debug builds, the dependencies are optimized (`[profile.dev.package."*"]`), so that the images decode and the window stays smooth during development. |
| Visual style | The tokens of the [Visual style](../specs.md#visual-style) in one Rust module, applied to the egui `Style` and `Visuals` | The mock-up and the application share the same values; changing a color or a size happens in one place. |
| Fonts | Manrope and JetBrains Mono, embedded in the executable from `assets/fonts/` | Both under the SIL Open Font License; the interface looks the same on every system, without depending on the installed fonts. |
| Icons | White SVG files tinted at runtime (`assets/icons/`, from [Lucide](https://lucide.dev), ISC license), the logo and the emblem from `assets/logo/`, rendered with `egui_extras` (SVG and PNG loaders); the simplest marks (chevron) are drawn with egui lines | SVG icons stay sharp at any display scale, and tinting one white file gives each state its color. |
| Linux display | X11 (XWayland under Wayland), chosen with `winit` when the event loop is built | The game runs through Proton as an X11 client, so an X11 application can read what it copies without having the focus; a native Wayland application can't always read the clipboard in the background. To be verified on Bazzite KDE in step 2. winit would pick Wayland otherwise (a dependency of eframe enables it), and the OpenGL renderer is only built for X11. |
| Clipboard | [`arboard`](https://github.com/1Password/arboard), polled every 250 ms on its own thread, which sends the copied items to the interface through a channel and wakes it up | Same API on Windows, macOS and X11, for reading the items and writing the whispers. Polling is simple and enough to react before the player looks at the window. On its own thread, a slow reading (under X11, the owner of the clipboard has to answer) never freezes the window, and the window only redraws when an item arrives. Only a hash of the last text is kept, not the texts copied outside the game. Two copies of the same item in a row leave the same text: change counters of each system (Windows, macOS) could tell them apart later, if needed. |
| Price-check hotkey (Linux, Windows) | [`global-hotkey`](https://github.com/tauri-apps/global-hotkey) to hear Ctrl+D (XGrabKey on the root window of X11, RegisterHotKey on Windows), the copy sent with the XTest extension of [`x11rb`](https://github.com/psychon/x11rb) at the release of D (step 14a1), with SendInput through [`enigo`](https://github.com/enigo-rs/enigo) at its press on Windows (step 14a2) | Under X11 (XWayland under Wayland), an application hears and sends keys while an X11 window, the game run by Proton, has the focus, as Exiled Exchange 2 does on Linux (uiohook). `global-hotkey` also covers Windows (RegisterHotKey), step 14a2, and macOS (Carbon), left out while Path of Exile 2 has no macOS client. The copy is sent once D is released: while the key is held, the passive grab gives every key to the application, so that a copy sent then wouldn't reach the game. The XTest keys are written with x11rb rather than `enigo`: it reads whether Ctrl is still held (QueryPointer), so as never to release a Ctrl the player holds (the next D would then reach the game alone), and never remaps a free keycode, which `enigo` does for a key missing from the layout. Checked on Bazzite KDE on 2026-11-01 with `xdotool` (an X11 window focused: heard and sent; a Wayland window focused: not heard); checked in the game by the owner the same day (every test passed, the class of the game `steam_app_2694490`). The grab holds for every X11 window, not only the game: until step 14c grabs the key only while the game is the active window, Ctrl+D becomes Ctrl+C in another X11 window (the Steam client), since a key grabbed can't be given back. On Windows, RegisterHotKey takes D alone and grabs no other key: the copy is sent at the press of D, when Ctrl is held (unless released within the few milliseconds the window takes to handle the message), C alone, as Exiled Exchange 2 does there (`pressKeysToCopyItemText` with `keepModKeys` in `main/src/shortcuts/Shortcuts.ts`), so that no crate is needed to read the state of Ctrl. `enigo` rather than the `windows` crate, whose calls are `unsafe`, forbidden in the application; it sends the virtual key of C, which Windows maps to the layout of the window that has the focus. Windows drops without a word the keys sent to a window of higher integrity (the game run as administrator): the log then says the copy was requested, not received. Not checked in the game on Windows: the owner has none. The CI of the pull requests runs Clippy on Windows and macOS, so that the code of these systems is compiled before a release. |
| Window over the game (Linux, step 14b1) | A second egui viewport, an X11 window *override-redirect* (`with_override_redirect`, `with_window_type(Tooltip)`, `with_active(false)` of `egui::ViewportBuilder`), placed from the pointer and the active window read through `x11rb` (`QueryPointer`, `_NET_ACTIVE_WINDOW`, `GetGeometry`); the click in the game that closes it seen by polling the buttons of `QueryPointer` while it is open | The way of Exiled Exchange 2 on Linux (electron-overlay-window sets override-redirect before mapping): the window manager doesn't manage the window, so KWin keeps it above the fullscreen game and never gives it the focus. Checked in the owner's game on 2026-11-01 with a throwaway probe (Bazzite KDE, windowed fullscreen, the game an X11 window of 2560 × 1440 with `_NET_WM_STATE_FULLSCREEN`, scale 1): the window shows over the game, the game keeps the keyboard, and a click on the window stays in it without reaching the game nor taking its focus. In exclusive fullscreen, the game copies nothing at Ctrl+D and D reaches it: not supported, as in Exiled Exchange 2. No new dependency. Windows in step 14b2: a window always on top shown without activation (`with_active(false)`), but winit can't make it never activated (`WS_EX_NOACTIVATE`) and `unsafe` is forbidden, so a click in it may take the focus of the game, to give back. |
| Price database | [poe2scout](https://poe2scout.com) public API (`https://api.poe2scout.com`, [Swagger](https://api.poe2scout.com/swagger)) | Covers the currency exchange items and the uniques of Path of Exile 2, gives the number of offers, the 7-day history, the leagues and the Exalted / Divine / Chaos rates. poe.ninja was rejected: its documentation asks desktop applications to go through their own backend rather than call its API from the players' machines. The prices are downloaded per category and cached, behind a trait, so that the source can change. |
| Price cache | One JSON file per league in the cache directory (`serde_json`), with a version number, written to a new file then renamed | The prices show at once at startup, and while the price database can't be reached; prices younger than an hour are not downloaded again at a new launch. A file of another version (the shape of the prices changed) is downloaded again rather than migrated. |
| Price estimation | One `trait` implementation per way of pricing, chosen by an `enum` of the item kinds: fixed-name items from the price database, the others estimated from similar offers | Each kind of item gets its price its own way, without changing the parser or the interface. |
| Item parser | A hand-written parser, section by section, with the words of each language in one table per language (`src/item/labels.rs`, from the client strings of Exiled Exchange 2, checked on copied items); no regular expressions | The structure of a copied item is the same in every language: only the words change, and adding a language is adding a table. Without dependency, and the Clippy lints that forbid what can panic (indexing, `unwrap`) apply to the whole parser, which reads every copied item. |
| Copy format | The advanced copy (the `{ … }` header of each modifier), and the copy of the trade of the game, without headers (step 13k2e): its lines read alone, as explicit modifiers without affix, tier nor range, those whose marker tells it as fractured, desecrated or Vaal (` (mutated)`); the affix and the tier of each found from its value in the modifier tables of the base (step 13k2e3) | The headers give the tier and the ranges of each modifier, which the roll bars, the range fields and the modifier tables need. The game writes them with Ctrl+C too (checked on 2026-10-28), but not for an item copied from the trade of the game (another player's listing, checked on 2026-10-28), which the parser refused until step 13k2e2: Exiled Exchange 2 reads it, each line alone (commit cca3066). The ranges of a unique come from the copy, or from poe2scout for a unique copied from the trade of the game, which has none (step 13k2e5): poe2scout writes the modifiers of each unique with their ranges in the answer already downloaded with the prices, kept in the price cache, and each copied line is matched with one of them by its stat, so that a French copy gets them too (the database writes in English only); Exiled Exchange 2 shows these lines as fixed and searches the unique by its name. |
| Offers | Official trade site API: `POST /api/trade2/search/poe2/<league>` then `GET /api/trade2/fetch/<ids>?query=<search id>&realm=poe2` for items (10 ids per fetch, from the ids of the search, the cheapest first), `POST /api/trade2/exchange/poe2/<league>` for the currency exchange (its offers in the answer, without fetch), on the trade site of the language of the item; the same queries as the links opened in the browser (`src/trade/query.rs`). Read on their own thread, which searches only when the player asks (checked on 2026-10-26) | The only source of individual offers: poe2scout only gives aggregates. The fetch returns the whole listed item (modifiers with their stat ids, item level, seller status, whisper message), used by the tooltip without another request. Accepted with guardrails despite the Terms of Use risk: see [Trade site usage](trade-site-usage.md). |
| Trade site limits | The limits read from the `X-Rate-Limit-*` headers of every answer, before its body, one policy per kind of request (search, fetch, exchange); two times kept for each request, when it left and when its answer or failure came; the hits the trade site counts beyond ours (a browser on the same address) added as if made at the answer; a request the limits don't allow is never sent, and a refusal waits for its `Retry-After` delay. When in doubt, the safe side: limits that can't be read keep the known ones, a request leaves the windows with the time of its answer, and only the requests the trade site counted for sure (a success with its limits, sent within the window) are taken from its counts; a margin of one second on every window and wait | The limits change without notice and the address may be shared: only the headers know them. Each count takes the time and the case on the safe side, so that the application never thinks a window has room the trade site doesn't give; four code reviews checked it (2026-10-26). |
| Stat filters | The stats of the copied item become filters of the search, as in Exiled Exchange 2: the trade id of each modifier line from the stats of Exiled Exchange 2 (strings of each language, `reduced` variants, trade ids by group), embedded, and the templates of `/api/trade2/data/stats` as a second lookup; equipment filters from `/api/trade2/data/filters` (checked on 2026-10-27: the item level and the quality in `type_filters` as `ilvl` and `quality`, the DPS and the augmentable sockets in `equipment_filters` as `pdps`, `edps` and `rune_sockets`, the required level in `req_filters` as `lvl`, searched as a maximum); the states in `misc_filters` (checked on 2026-10-28: `corrupted`, `sanctified`, which isn't corrupted (2,706 rare rings sanctified and not corrupted), `mirrored` (33 rare rings), and for step 13k2d `twice_corrupted`, `fractured_item`, `desecrated`, `mutated` and `veiled`; checked on 2026-10-29 that the trade site applies `{ "option": "true" }` on the two states of step 13k2d: `fractured_item` finds 10 rare rings online, and `twice_corrupted`, none among the rare rings online but more than 10,000 items of any status, its first 10 all flagged `doubleCorrupted` and `corrupted` in their offers), the number of unrevealed modifiers as the pseudo stat `pseudo.pseudo_number_of_unrevealed_mods`, and the Runic Ward of a runeforged base in `equipment_filters` as `ward`, the category of the base searched in place of the base type when the player unchecks it (`type_filters.category`, the ids of Exiled Exchange 2, checked on 2026-10-28; a flask by its tags, `flask.life` or `flask.mana`); the ranges of a unique from the advanced copy. A modifier added by a Vaal orb on a unique (mutated, `{ Vaal Unique Modifier }`) is an explicit line of the trade site, flagged `mutated` in its offers: its explicit id finds it (checked on 2026-10-28 on Soul Tether; `/api/trade2/data/stats` has no mutated group). See [Game data](game-data.md) | Offers are only comparable with similar stats; the same filters price the uniques, the rare, magic and normal items and the jewels. The trade site templates alone miss the `reduced` variants and the local stats; Exiled Exchange 2 found every line of the copied items of the tests, in English and French (2026-10-26). An exceptional base is searched by its sockets and its quality: the trade site refuses its name ("Unknown item base type", checked on 2026-10-27). |
| Modifier tiers | The tier and its range from the advanced copy; the range of every tier of a modifier from the modifiers, bases and stat texts of the RePoE fork (`mods.json`, `base_items.json`, `stat_descriptions.json`), reduced by a generator kept in the repository, committed and embedded, generated again after each patch of the game. See [Game data](game-data.md) | The roll bar of a rare modifier covers all its tiers, so that a full bar means close to the best possible; the advanced copy only gives the range of the current tier. RePoE gave back the tier and range of the copied items of the tests (2026-10-26) and of 374 modifiers of offers of the trade site (2026-10-27); poe2db has no API. Embedded, the data works offline and matches the parser of the same version. |
| Game data | A generator in Rust, `tools/game-data/`, a member of the Cargo workspace (`cargo run -p game-data`), writing one stat or one base per line (NDJSON) to `assets/game-data/`; the files embedded with `include_str!` and read at the first item copied in their language; the stat of a line found by its string, its numbers written `#` | The language of the application, without another tool to install; one stat or base per line makes the changes of a patch readable in a diff; reading a language takes 3 ms in a release build, so no build script is needed. The release workflow takes the default member of the workspace, so that the generator is never published. See [Game data](game-data.md). |
| Estimated price | Median of the 5 cheapest similar offers, suspicious offers excluded; an offer is suspicious under a quarter of the median of the first 10 offers, the answer to the search, fewer when some were withdrawn since the search (`src/estimate.rs`) | A median resists the bait offers and the few overpriced ones; 5 offers are enough to be meaningful without extra requests (one fetch returns 10). The estimate can't tell its own suspicious offers (it leaves them out): the median of the whole first page holds while fewer than half of it are bait, which a median of the 5 cheapest wouldn't (3 baits of 5 would make the reference a bait), and it doesn't move when the next offers load. |
| Item names in French | Trade site data in both languages (`/api/trade2/data/items`, `/data/static` and `/data/stats` on `www.` and `fr.pathofexile.com`, six requests one second apart), read on their own thread, cached and refreshed once a day; the old names stay when the trade site can't be reached, with a new attempt every hour, every minute while no name is known (but not after a refusal of the trade site). The templates of the stats (`/data/stats`) come with them since step 13d, as a second lookup of the stat of a line (see [Game data](game-data.md)) | The price database only knows the English names. The items of the currency exchange have ids shared by both languages and by poe2scout (all of them on 2026-10-25): a French name gives the id, which gives the price, without translation. The uniques have no id, but each category lists them in the same order in both languages (771 pairs without a contradiction on 2026-10-25), checked again at each download: a category whose lists don't line up (another number of uniques, a variant in one language only, a base type paired two ways) is left out rather than paired wrong, and an answer without a kind of names keeps the cache. An unidentified unique can be each unique of its base known by the trade site, priced or not: the price database only has the uniques listed lately. The base types don't line up (some are missing in French) and need no translation: the base of a magic item is found among those of its language, and the searches use the trade site of its language. |
| Images | Orb icons, logo and emblem bundled from `assets/` | See [Images](images.md). |
| HTTP | [`ureq`](https://github.com/algesten/ureq) in a background thread, `serde` / `serde_json` | Blocking and simple; the requests are few (one price refresh per hour, one trade site search per click), so an async runtime is not needed. The interface thread is never blocked. |
| Interface translations | [Fluent](https://projectfluent.org) with `fluent-bundle`, files `locales/en.ftl` and `locales/fr.ftl` embedded in the executable | Handles the plural rules ("1 stat", "6 stats"; "0 offre", "0 offers"), and switching the language at runtime, needed by the language setting. The language of the system is read with [`sys-locale`](https://github.com/1Password/sys-locale), small and without other dependency. The interface doesn't follow the language of the copied items: it would change without the player asking (decided on 2026-10-24). |
| Local files | [`directories`](https://github.com/dirs-dev/directories-rs) for the configuration, cache and log directories; the settings in TOML with `serde` and [`toml`](https://github.com/toml-rs/toml), written to a new file then renamed; the size and position of the window kept by eframe (`persistence` feature, `window.ron` next to the settings, without the state of the widgets) | Standard locations on each system. A crash while saving never leaves half a settings file. eframe brings the window back onto a connected screen when its screen is gone, which the application can't do itself: the screens are unknown before the window opens (decided on 2026-10-24). |
| Log | The [`log`](https://github.com/rust-lang/log) facade and [`simplelog`](https://github.com/Drakulix/simplelog.rs): a file per session (the previous one kept), the error output in debug builds, the panics logged | The standard facade, also used by egui and eframe; `simplelog` writes a file without extra setup. Enough to follow the application and debug it on a player's machine, where there is no console. |
| Price history chart | [`egui_plot`](https://github.com/emilk/egui_plot) | Made for egui, no other dependency (wide layout, step 24). |
| Releases | GitHub Actions workflow triggered by version tags, portable archives (no installer) | Builds every system on its own runner and publishes the archives with `gh release`, without extra tooling. A portable executable is enough for version 1. The Linux executable targets glibc rather than musl: a statically linked musl executable can't load the system's graphics libraries (OpenGL, X11). |
